## 已准备的运行方式

- 独立域名、专用系统用户、单进程 Waitress；Studio 继续负责账号、队列和计费。
- production.env.example 提供有范围校验的线程数、连接数及空闲连接超时；默认 8/100/120，属于起始配置，不是容量承诺。
- Nginx 仅直出 /_next/static/ 带版本资源；页面、API、非哈希素材继续由应用提供。Cloudflare 不得使用覆盖全站的 Cache Everything；登录、API 和私有结果必须绕过共享缓存。
- /healthz 只表示本服务及静态入口就绪。另用不带凭据的 Studio 健康检查与实际授权验收判断依赖是否可用，不能把 TCP 可达当作联动成功。
- 现有 verify_release.py 检查包整体摘要及逐文件内容。预构建包不带用户数据、证书、官方凭据或虚拟环境。

## 功能完成后才能执行

1. 确定两个仓库的发布范围，固定提交；在干净的隔离构建目录生成前端，不从正在开发的 out 目录制作最终包。
2. 通过 Studio 原有 CI 验证和发布流程准备对应版本及迁移；记录兼容关系，不把其他任务的未完成改动一并发布。
3. 在 Linux 隔离环境运行后端测试、Nginx 配置检查及真实 HTTP 静态资源对照。验证 /api 和私有结果不能被静态规则绕过，缺失静态资源返回 404。
4. 最新重绘流程验收：蒙版、预览、应用、导出、中断恢复；补验普通批次、放大和 Director 的二进制领取。只使用合成数据与模拟上游。
5. 用慢客户端并发下载合成图片，同时查询任务及访问登录，记录延迟、超时、线程/连接、RSS 和临时磁盘占用；根据服务器余量确定资源预算。不能用本机空闲内存推导生产容量。
6. 演练服务重启、Studio 暂不可达、图片过期、旧版本回退。重启后会话失效是当前限制；验证重新登录只恢复已有任务、不重发生成。
7. 保存数据库和数据目录备份；提前验证新增数据库结构是否支持旧代码。需要恢复数据库时必须先停写并另行制定恢复步骤，禁止自动降级或覆盖在线数据库。
8. 最终发布得到明确授权后，先发布兼容的 Studio 版本，再把 Idlecloud 安装到全新版本目录。启动验证通过后接入正式反向代理与侧栏入口。
9. 先由指定试用用户验收；真实出图需要明确模型、数量和费用范围。观察期内出现登录失败、重复提交/计费、跨用户访问或持续错误，应停止放量。

## 回滚执行顺序

1. 停止引入新 Idlecloud 请求，保留 Studio 原服务；不要为了回滚删除任务或恢复摘要。
2. 停止 Idlecloud，切换 current 到已核验的旧版本，再启动并检查健康、登录和恢复。
3. 若旧版本不兼容当前 Studio 接口，先保持 Idlecloud 关闭，按已记录的兼容方案恢复；不盲目回滚 Studio 数据库。
4. 数据格式未变时保留现有用户目录。若必须恢复数据，先保留故障现场备份，恢复到新目录，不能覆盖唯一副本。
